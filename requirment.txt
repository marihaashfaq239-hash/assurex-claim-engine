AssureX Claim Engine — Complete Project Flow

Hunain, tumhari Aptech ki SRS ke mutabiq project ka naam AssureX Claim Engine hai. Ye ek AI-powered warranty claim management web application hai jo manufacturers aur service centers ko warranty claims validate karne mein help karegi.

Main tumhein simple Roman Urdu mein samjhata hoon:

Project ka main purpose kya hai

1. Project ka Main Purpose

Example: Ek customer ne 1 saal pehle AC khareeda tha. Ab AC kharab ho gaya aur customer warranty claim submit karta hai.

AssureX system automatically:

Customer ki purchase receipt aur warranty card check karega.
OCR se documents ka data extract karega.
Product ki warranty validity check karega.
Python ML model se claim predict karega.
Google Teachable Machine se bhi claim classify karega.
Dono AI models ke results compare karega.
Warranty rules, missing documents aur contradictions check karega.
Final result dega: Likely Valid, Likely Invalid ya Manual Review Required.

Important: AI ka result final legal approval nahi hoga. Uncertain ya conflicting claims authorized reviewer ke paas jayenge.

Ab system dono models ke results compare karega.

Example:

Confidence Difference = |92 − 88| = 4%

Likely Valid	Claim valid hone ke indicators hain
Likely Invalid	Claim invalid hone ke indicators hain
Manual Review Required	Human reviewer ki zaroorat hai

1.1 Background and Necessity for the Application
Warranty claim management is vital for manufacturers and service centers, as
it directly affects customer satisfaction, operational efficiency, and financial
control. Traditional claim-evaluation methods require employees to manually
examine purchase details, product age, fault descriptions, repair history,
supporting documents, and warranty conditions. This process is timeconsuming and prone to errors, inconsistent decisions, duplicate claims,
overlooked exclusions, and delays in claim approval. The AssureX Claim Engine
aims to automate and improve this process through Python-based Web
development, machine learning, and intelligent claim-analysis techniques.
The ‘AssureX Claim Engine’ reduces the requirement for completely manual
warranty verification by automatically analyzing the information and documents
submitted with a claim. The application analyses product details, purchase
information, reported faults, repair history, warranty coverage, and supporting
documents to determine whether a claim is valid, invalid, or requires manual
review. It also generates a confidence score using a Python classification model
and compares the result with a separately trained Google Teachable Machine
model. By combining machine-learning predictions with warranty-condition
checks, the application improves consistency, identifies uncertain or conflicting
claims, and supports faster and more reliable decision-making. The goal is to
deliver a secure, accurate, and accessible solution that enhances warranty claim
processing for manufacturers and service centers.
© Aptech Limited
1.2 Proposed Solution
The proposed solution introduces an AI-powered, Web-based warranty claim
validation application that helps manufacturers and service centers evaluate
claims accurately and efficiently. Users enter product age, purchase
information, fault details, repair history, warranty conditions, and supporting
evidence through the application. The application processes these details using
a Python-based classification model and predicts whether the claim is likely to
be valid, invalid, or require manual review.
The AssureX Claim Engine generates confidence scores for all three claim
categories and applies warranty validation rules to support the prediction. The
same claim information is then converted into a visual Claim Summary Card
and evaluated using a separately trained Google Teachable Machine model. The
application compares the predicted class and confidence scores produced by
both models. This approach improves reliability, identifies uncertain or
conflicting claims, and supports faster and more consistent warranty decisions.
© Aptech Limited

The development phase of the application includes following steps:
Step 1: Claim Data Collection
The user enters product details, purchase information, fault description, repair
history, warranty conditions, and other required information through the Webbased interface. Supporting documents such as purchase receipts, warranty
cards, product images, and repair records are also uploaded. Each submitted
claim is assigned a unique Claim ID.
Step 2: Data Extraction and Validation
The application extracts relevant information from the uploaded documents and
compares it with the details entered by the user. It checks missing fields, invalid
dates, unsupported file formats, incorrect values, and inconsistencies such as
mismatched serial numbers or purchase information.
Step 3: Data Pre-Processing
The validated claim data is cleaned and prepared for classification using Python.
This includes handling missing values, converting date formats, encoding
categorical fields, normalizing numerical values, and creating derived features
such as product age, remaining warranty period, and number of missing
documents.
Step 4: Dataset Creation
A structured warranty claim dataset is created containing Valid Claim, Invalid
Claim, and Manual Review records. The dataset must include normal,
incomplete, contradictory, complex, and borderline claim scenarios. The
structured dataset is used to train and test the Python classification model.
Step 5: Python Classification Model Training
Different machine learning classification algorithms are trained and evaluated
using Python. Their performance is compared using accuracy, precision, recall,
F1-score, confusion matrix, and class-wise results. The best-performing model
is selected and integrated into the Web application.
© Aptech Limited
Step 6: Python Claim Classification
The pre-processed structured claim data is submitted to the trained Python
model. The model predicts whether the claim is valid, invalid, or requires manual
review and generates confidence scores for all three classes.
Step 7: Claim Summary Card Generation
The same pre-processed claim data is independently converted into a
standardized visual Claim Summary Card. The card contains claim information
such as product age, warranty period, fault category, repair history, receipt
availability, serial-number status, and missing documents.
The Claim Summary Card must not contain the Python model prediction,
confidence score, or final claim result.
Step 8: Google Teachable Machine Model Training
The Claim Summary Card images are grouped into three classes: Valid Claim,
Invalid Claim, and Manual Review. These images are used to train a separate
image-classification model using Google Teachable Machine.
Step 9: Google Teachable Machine Classification
The Claim Summary Card generated for a submitted claim is provided to the
trained Google Teachable Machine model. The model independently predicts the
claim class and generates confidence scores for all three categories.
Step 10: Model Prediction and Confidence Comparison
The application compares the results produced by the Python classification
model and the Google Teachable Machine model. It verifies whether both models
predict the same class and calculates the difference between their confidence
scores.
© Aptech Limited
The confidence difference must be calculated using:
Confidence Difference =
|Python Model Top-Class Confidence
− Google Teachable Machine Top-Class Confidence|
The two models are independently trained and therefore are not required to
generate exactly identical confidence scores.
Step 11: Warranty Rule Validation
The application verifies business conditions such as warranty expiry, product
age, fault coverage, purchase proof, serial-number match, previous repairs,
excluded damage, duplicate claims, and missing documents. These checks
support or challenge the predictions generated by the two models.
Step 12: Final Claim Decision
The final recommendation is generated by considering the Python model result,
Google Teachable Machine result, confidence-score difference, warranty rules,
missing evidence, and detected contradictions. The claim is then classified as
Likely Valid, Likely Invalid, or Manual Review Required. Claims with low
confidence, conflicting predictions, incomplete documents, or rule violations
must be sent for manual review.

The purpose of this document is to outline the design, functionality, and
implementation plan of the proposed AssureX Claim Engine. This document

1.4 Scope of Project
The scope of this project is to design and implement an AI-powered, Web-based
warranty claim validation application that assists manufacturers and service
centers in evaluating warranty claims. The application will collect claim details
and supporting documents, process the information using a Python
classification model, compare the result with a Google Teachable Machine model,
and classify the claim as Valid, Invalid, or Manual Review. It aims to reduce
manual effort, improve decision consistency, identify incomplete or conflicting
claims, and support faster claim processing. Integration with live manufacturer
databases, payment systems, or enterprise warranty platforms falls outside the
scope of this project.
© Aptech Limited
1.5 Constraints
The AssureX Claim Engine project faces certain constraints such as
dependency on the quality, completeness, and accuracy of the submitted claim
details and supporting documents. The application’s effectiveness is limited by
the size, balance, and reliability of the training dataset. Differences may also
occur between the confidence scores generated by the Python model and Google
Teachable Machine. Privacy and security concerns regarding the storage and
handling of customer, purchase, and warranty information must also be
addressed in accordance with applicable data protection regulations.

ii. User Profile Management - Users should be able to create and update

The application should maintain a unique User ID for each registered

products by entering details such as product name, category, brand,
model number, serial number, purchase date, purchase price, retailer,
and warranty duration. Each registered product should be assigned a
unique Product ID.
iv. Warranty Record Management - The application should store standard
and extended warranty information, including warranty provider, start
date, expiry date, coverage conditions, exclusions, and service-center
details. Users should be able to view all active, expired, and approaching
expiry warranties from a common interface.
© Aptech Limited
v. Receipt and Invoice Upload - Users should be able to upload and
securely store purchase receipts, invoices, warranty cards, and other
proof-of-purchase documents in formats such as PDF, JPG, JPEG, and
PNG.
vi. Receipt Scanning and Data Extraction - The application should extract
important information from uploaded receipts and invoices, including
purchase date, invoice number, product name, model number, serial
number, retailer, purchase amount, and warranty duration.
vii. Extracted Data Verification - The application should display the
information extracted from uploaded documents and allow users to review
and correct inaccurate or incomplete values before saving or submitting
the claim.
viii. Warranty Tracking - The application should automatically calculate
warranty start and expiry dates and display the remaining warranty
period. It should identify whether a product warranty is active, expired,
nearing expiration, or covered under an extended warranty.
ix. Warranty Expiry Alerts - The application should notify users when a
registered product warranty is approaching its expiry date.
Administrators should be able to configure the number of days before
expiry when an alert should be generated.
x. Claim Registration - The application should allow users or service-center
employees to create a new warranty claim. Each submitted claim should
be assigned a unique Claim ID and linked to the corresponding user,
product, warranty, and supporting documents.
xi. Claim Information Collection - The application should collect claim
information such as product age, purchase details, fault occurrence date,
fault description, damage type, warranty conditions, service history,
previous replacement details, and claim submission date.
xii. Fault and Damage Evidence Upload - Users should be able to upload
product photographs, damage images, fault videos, serial-number
photographs, diagnostic reports, and other supporting evidence required
for claim evaluation.
© Aptech Limited
xiii. Repair History Management - The application should record previous
repair dates, repair-center details, replaced parts, repair outcomes, repair
costs, and whether each repair was completed by an authorized or
unauthorized service center.
xiv. Document Organization - The application should organize uploaded
receipts, warranty cards, repair reports, product images, and other
supporting documents under the relevant product and claim record.
Users should be able to view, download, replace, or remove documents
according to their access rights.
xv. Data Validation - The application should check mandatory fields, date
formats, numerical values, uploaded file types, file sizes, and duplicate
Claim IDs. It should prevent incomplete or invalid information from being
submitted without appropriate warnings.
xvi. Data Pre-Processing - The submitted claim data should be cleaned and
prepared using Python. This should include handling missing values,
converting date formats, encoding categorical values, normalizing
numerical values, and creating derived fields such as product age,
remaining warranty period, and missing-document count.
xvii. Common Warranty Claim Dataset - The application should use a
structured dataset containing valid, invalid, and manual-review warranty
claim records. The same underlying claim records should be used in CSV
or tabular form for the Python model and converted into Claim Summary
Card images for Google Teachable Machine.
xviii. Python Classification Model - The application should use a machine
learning classification model trained using Python. Students should train
and compare suitable algorithms and select the best-performing model to
classify a submitted claim as Valid Claim, Invalid Claim, or Manual
Review.
xix. Python Confidence Score Generation - The Python classification model
should generate confidence scores or class probabilities for all three claim
categories. The application should display the predicted class and
corresponding confidence values.
© Aptech Limited
xx. Claim Summary Card Generation - The application should
automatically convert the pre-processed claim information into a
standardized visual Claim Summary Card. It should contain product age,
warranty status, fault type, repair history, document availability, serialnumber status, and other relevant claim information.
The Claim Summary Card should not contain the Python model
prediction, Python confidence score, or final claim decision.
xxi. Google Teachable Machine Classification - The Claim Summary Card
should be evaluated using a separately trained Google Teachable Machine
image-classification model. The model should independently classify the
claim as Valid Claim, Invalid Claim, or Manual Review and generate
confidence scores for all three classes.
xxii. Model Prediction Comparison - The application should compare the
class predicted by the Python classification model with the class predicted
by the Google Teachable Machine model. It should clearly display whether
the predicted classes match.
xxiii. Confidence Score Comparison - The application should compare the
top-class confidence scores generated by the Python and Google
Teachable Machine models. It should calculate and display the absolute
difference between the two confidence scores.
xxiv. Model Consistency Status - The application should classify the
comparison as Strong Match, Acceptable Match, Weak Match, Model
Disagreement, or Uncertain Result based on configurable confidencedifference and minimum-confidence thresholds.
xxv. Warranty Rule Validation - The application should independently
validate business rules such as warranty expiry, fault coverage, claim
reporting period, proof of purchase, extended warranty, serial-number
match, previous repairs, product replacement, excluded damage, and
required documents.
© Aptech Limited
xxvi. Configurable Warranty Policies - Warranty periods, covered faults,
exclusions, reporting deadlines, mandatory documents, and repair
conditions should be stored in configurable files or a database. The
application should support different warranty rules for different product
categories.
xxvii. Serial-Number Verification - The application should compare the serial
number entered by the user with serial numbers extracted from the
receipt, warranty card, product image, and repair records. A mismatch
should generate a warning or route the claim for manual review.
xxviii. Contraction Detection - The application should identify conflicting
information such as a claim date before the purchase date, a repair date
before purchase, inconsistent product models, conflicting serial numbers,
or a fault date after the claim submission date.
xxix. Missing Document Detection - The application should identify missing
mandatory documents such as the purchase receipt, warranty card,
product image, serial-number evidence, fault evidence, or repair report. It
should inform the user which documents are required.
xxx. Duplicate Claim Detection - The application should detect possible
duplicate claims by comparing Claim IDs, invoice numbers, product serial
numbers, fault descriptions, claimant details, document hashes, and
previous claim records.
xxxi. Document Duplicate Detection - The application should create a secure
hash for uploaded documents and detect whether the same receipt,
invoice, warranty card, or evidence file has already been used in another
claim.
xxxii. AI-Generated Claim Summary - The application should generate a clear
summary of the product, warranty coverage, reported fault, repair history,
uploaded evidence, detected issues, and claim status to help users and
reviewers understand the claim quickly.
© Aptech Limited
xxxiii. Claim Preparation Assistance - Before final submission, the application
should guide the user by displaying missing information, missing
documents, approaching deadlines, possible contradictions, and
recommended corrective actions.
xxxiv. Final Claim Decision - The application should generate the final result
by considering the Python model prediction, Google Teachable Machine
prediction, confidence-score difference, warranty rules, missing
documents, duplicate indicators, and contradictions.
The final result should be one of the following:
• Likely Valid
• Likely Invalid
• Manual Review Required
xxxv. Decision Explanation - The application should explain the factors
supporting the decision, factors opposing the decision, rules passed, rules
failed, detected contradictions, and additional evidence required.
xxxvi. Manual Review Workflow - Claims with low confidence, conflicting model
predictions, missing evidence, duplicate indicators, or rule violations
should be added to a manual-review queue. An authorized reviewer
should be able to approve, reject, or request additional information.
xxxvii. Reviewer Comments and Decision Override - Authorized reviewers
should be able to add comments and override the automated
recommendation. The original AI results and reasons for the override
should remain available in the audit history.
xxxviii. Claim Status Tracking - Users should be able to track the progress of a
submitted claim through stages such as Draft, Submitted, Under
Evaluation, Additional Information Required, Manual Review, Approved,
Rejected, and Closed.
© Aptech Limited
xxxix. Notification and Alerts - The application should notify users about
warranty expiry, claim submission, missing documents, requests for
additional information, status changes, review completion, approval, or
rejection.
xl. Claim Dashboard - Users should have access to a dashboard displaying
registered products, active warranties, expiring warranties, saved
receipts, submitted claims, pending actions, and recent claim decisions.
xli. Administrator Dashboard - The application should provide
administrators with a dashboard displaying total claims, valid claims,
invalid claims, manual-review claims, pending claims, duplicate alerts,
model disagreements, average confidence scores, and claim trends.
xlii. Search and Filtering - Users and administrators should be able to search
and filter warranty and claim records using Claim ID, Product ID, product
category, serial number, warranty status, claim status, risk level,
confidence range, reviewer, and date range.
xliii. Data Analysis and Reporting - The application should generate analytics
on claim outcomes, frequently reported faults, rejected claim reasons,
product categories, warranty expirations, repair patterns, model
performance, and manual-review frequency.
xliv. Downloadable Claim Report - The application should generate a
downloadable report containing the claim details, uploaded evidence,
warranty status, Python model result, Google Teachable Machine result,
confidence comparison, rule-validation result, contradictions, final
recommendation, and reviewer comments.
xlv. Data Export - Administrators should be able to export selected claims,
product, warranty, and analytics records in CSV or Excel-compatible
format.
© Aptech Limited
xlvi. Data Storage - The application should use a secure relational or NoSQL
database to store user accounts, products, warranties, receipts, claims,
repair histories, predictions, confidence scores, rule results, notifications,
and audit records.
xlvii. Audit Trail - The application should record important actions such as
account creation, product registration, document upload, extracted-data
correction, model prediction, claim submission, status change, reviewer
action, and final decision.
xlviii. Model Version Tracking - Each claim prediction should be linked to the
version of the Python and Google Teachable Machine models used during
evaluation. Updating a model should not alter previously recorded results.
xlix. Error Handling - The application should display understandable error
messages for invalid files, incomplete claim data, failed document
extraction, unavailable models, database errors, and unsuccessful
predictions without exposing technical system details.
l. Monitoring and Anomaly Alerts - The application should monitor failed
uploads, repeated login attempts, duplicate documents, unusual claim
activity, model failures, low-confidence predictions, and excessive
disagreement between the two models. Appropriate alerts should be
generated for administrators.
In addition, the application should provide a responsive and user-friendly Web
interface that can be accessed through desktop, tablet, or mobile browsers. The
interface should allow users to organize receipts, track warranties, prepare
claims, view AI-generated summaries, monitor claim progress, and receive alerts
before warranty or claim deadlines. These capabilities reflect the workflow
demonstrated by the reference application while extending it with claim
validation, dual-model comparison, business-rule verification, duplicate
detection, and administrative review.
© Aptech Limited
1.7 Non-Functional Requirements
There are several non-functional requirements that should be fulfilled by the application
which are as follows:

Performance: The application should process uploaded claim details and
generate predictions from both models within five seconds under normal
operating conditions.
Scalable: The application should be able to store and manage at least
10,000 warranty claims and support multiple manufacturers, service
centers, products, and concurrent users without significant performance
degradation.
Usable: The application should provide an intuitive and user-friendly Web
interface for customers, service-center employees, reviewers, and
administrators.
Accuracy: The Python classification model and Google Teachable Machine
model should achieve an overall accuracy of at least 85% on unseen test
claims and should reliably identify claims requiring manual review.
© Aptech Limited
Available: The application should remain operational during business
hours with at least 99% up time to ensure uninterrupted claim
submission, evaluation, tracking, and review.
